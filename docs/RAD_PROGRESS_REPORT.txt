EDUSCAN CAPSTONE PROJECT
RAPID APPLICATION DEVELOPMENT (RAD) PROGRESS REPORT

Project Title:
EduScan: A Web-Based Facial Recognition System for Automated Attendance and Grading Reports for San Jose National High School

Reporting Period:
2026-07-23 to 2026-08-17

Prepared For:
Capstone project progress reporting and group presentation

Methodology:
Rapid Application Development (RAD)


1. PURPOSE OF THIS REPORT

This report documents the actual progress of EduScan according to the four primary stages of the Rapid Application Development methodology:

- Requirements Planning
- User Design
- Rapid Construction
- Cutover

The report distinguishes implemented and tested functions from activities that still require real school deployment, stakeholder approval, hardware testing, or user evaluation. The dates are based on the available Git commit, project files, implementation records, and completed verification work. The original repository contains only one initial batch commit; therefore, later accomplishments are grouped by the dates on which the working system files and verification results were completed.


2. PROJECT OBJECTIVES COVERED BY THE RAD PROCESS

- Develop attendance monitoring for students, faculty, and non-teaching personnel.
- Deliver SMS notifications for time-in, time-out, tardiness, and absence events.
- Allow teaching staff to encode, manage, and monitor grades per subject.
- Generate attendance, absence, tardiness, grading, temporary attendance, and official SF2 reports.
- Prepare the system for ISO 25010 evaluation in functional suitability, performance efficiency, compatibility, usability, and reliability.


3. RAD STAGE 1: REQUIREMENTS PLANNING

Status:
Completed for the current capstone implementation scope. Requirements may still be refined through formal school user acceptance testing.

Purpose of the Stage:
The group identifies the school problem, project scope, stakeholders, required information, operational rules, legal constraints, and acceptance criteria before construction begins.

Stakeholders Identified:

- School administrators
- Teachers and class advisers
- Students
- Parents or guardians
- Faculty members
- Non-teaching personnel
- Gate security guards
- School records personnel
- School Data Protection Officer
- Capstone researchers and evaluators

Requirements Established:

- A secured laptop and camera will operate as the attendance station at the school gate.
- Students, faculty, and non-teaching personnel must be supported by the attendance system.
- A verified face match must create a real attendance event in the local database.
- Verified matches must alternate between time-in and time-out to support multiple exits and re-entries during the same day.
- A camera frame may contain more than one face, and each distinct enrolled person must be processed independently.
- The first arrival may be classified as late using the teacher-defined class schedule and grace period.
- Teachers and administrators may correct attendance records, but the original gate event must remain available for audit.
- Daily absence closing must run automatically at the authorized cutoff.
- Weekends, holidays, suspended classes, special schedules, and excused absences must not be handled as ordinary school days.
- SMS events must cover time-in, time-out, tardiness, and absence.
- The intended SMS gateway is a school-controlled Android phone operating on the secured local network.
- Teachers must be able to configure quizzes, summative tests, periodic tests, overall-grade inputs, weights, and passing rules.
- Gradebooks must be organized by school year, grading period, quarter, grade level, section, and subject.
- Every gradebook change must record the responsible user, reason, previous state, new state, and date.
- Attendance must first be available in a temporary spreadsheet and then transferred into the official SF2 format.
- Male and female learners must be placed in the correct SF2 row blocks.
- Learner names must be alphabetically arranged within the appropriate male or female SF2 block.
- The system must provide administrative maintenance for users, students, employees, grade levels, sections, subjects, and academic periods.
- Approved school roster spreadsheets must be validated before import.
- Biometric deletion and complete school-record disposal must be separate actions.
- Complete disposal must remove linked attendance, correction, grade, SMS, intervention, excused-absence, and biometric records while retaining a non-identifying disposal audit.
- SQLite and the matching biometric encryption key must be backed up and restored as one protected recovery set.
- Database changes must be recorded through versioned migrations.
- Privacy controls must reflect transparency, legitimate purpose, proportionality, safeguards, role-based access, correction procedures, retention, and authorized disposal.

Non-Functional Requirements Established:

- Local processing of facial recognition data
- Role-based access control
- Password-protected accounts
- Encrypted biometric samples and LBPH model files
- Database referential-integrity checks
- Auditable attendance and grade changes
- Reliable local operation during normal school use
- Recoverable database and encryption-key backups
- Compatibility with a browser camera, SQLite, official XLSX reports, and an Android SMS gateway
- Usable administrator, teacher, and scanner interfaces

4. RAD STAGE 2: USER DESIGN

Status:
Completed for the current working interface. Additional refinements may be introduced after formal student, teacher, and staff evaluation.

Purpose of the Stage:
Users and developers refine the required workflows, screen organization, data entry, outputs, and corrections through rapid interface iterations. In EduScan, the initial frontend interfaces acted as the first design iteration, while subsequent screens were connected to real backend processes and revised based on clarified requirements.

Initial Design Iteration:

- [2026-07-23]: The initial EduScan frontend interfaces were committed as one batch under commit e3fc94c, titled “Initial commit: EduScan Frontend Interfaces.”
- [2026-07-23]: Initial screens represented the administrator dashboard, attendance, grading, reports, teacher functions, and scanner interface.

User Workflow Design Completed:

- Administrator workflow: sign in, manage system configuration, review attendance, correct records, manage gradebooks, generate reports, manage school data, manage accounts, import rosters, and perform backup or recovery.
- Teacher workflow: review assigned learners, attendance, truancy interventions, corrections, and grade information within authorized access.
- Scanner workflow: use a dedicated gate account, enable the local camera, recognize one or more enrolled people, and record alternating time-in and time-out events.
- Enrollment workflow: create or select an authorized person, verify consent, capture sufficient face samples, train the LBPH model, and retain enrollment audit history.
- Biometric maintenance workflow: view enrollment details, replace face samples, remove biometric information, and retain a non-biometric change log.
- Full disposal workflow: select a school record separately from biometric maintenance, enter the authorization reference and reason, confirm the subject identifier, remove linked records, and retain a non-identifying disposal audit.
- Attendance-correction workflow: compare the raw event with supporting evidence, enter corrected status or time, provide a reason, and preserve the original event.
- Calendar workflow: record holidays, suspensions, special schedules, and authorized excused absences.
- Gradebook workflow: select school year, quarter, grade level, section, and subject; configure grade components; enter scores; provide a reason; save; and review grade-change history.
- SF2 workflow: select the reporting month and class, generate the official workbook, verify sex-specific placement and alphabetical order, and retain the output for records review.
- Roster workflow: choose an approved XLSX file, enter its approval reference, validate the rows, review errors, and import only after successful validation.
- Recovery workflow: create an encrypted recovery package, store the passphrase separately, download an off-device copy, verify a backup before restoration, stage the restore, and restart the server to apply it.

Data Design Completed:

- Structured identity, attendance, grading, schedule, calendar, user, audit, and configuration records are stored in SQLite.
- Biometric samples are stored as encrypted files outside the website’s public directory.
- SQLite stores the structured metadata that links each encrypted sample to an authorized person.
- The trained LBPH model is stored as an encrypted file with version and integrity metadata in SQLite.
- The temporary attendance workbook and official SF2 workbook are generated from validated database records.
- Backup packages contain the SQLite database, encryption key, face samples, LBPH models, and SF2 templates as one encrypted recovery set.

Process Design Completed:

- Face enrollment to encrypted sample storage to LBPH training
- Camera frame to multiple-face detection to LBPH comparison to attendance events
- Attendance event to temporary workbook to reviewed SF2 report
- Attendance event to SMS outbox to Android gateway
- Teacher grade input to weighted initial grade to transmuted grade to grade audit
- Approved roster workbook to validation preview to database import to alphabetical SF2 placement
- Authorized full disposal to linked-record deletion to anonymous disposal audit
- Secure backup creation to off-device storage to verified staging to controlled restoration
